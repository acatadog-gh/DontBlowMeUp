# 《别炸我！》联机版（M2）方案与准备清单

> 版本：v1.0（2026-10-29）　前置：WebGL 版已上线，规则 v0.9.2 冻结
> 原则：**复用现有 GDScript 逻辑，不做第二套规则实现**

---

## 一、技术选型（为什么这么定）

### 传输：WebSocket（不用 ENet）

Godot 自带高性能网络（ENet/UDP），但 **浏览器里跑不了 UDP**——我们的主力平台是 WebGL，所以传输层必须用 WebSocket（`WebSocketServer` / `WebSocketClient`，Godot 原生支持，浏览器兼容好）。

回合制卡牌每步只传几十字节，WebSocket 完全够用，不需要 WebRTC。

### 架构：专用权威服务器（不用"房主当服务器"）

```
┌─────────────┐   WebSocket(wss)   ┌──────────────────┐
│ 玩家A(浏览器) │ ◄───────────────► │                  │
├─────────────┤                    │  Godot 无头服务器  │
│ 玩家B(浏览器) │ ◄───────────────► │  （跑现有规则逻辑） │
├─────────────┤                    │  房间管理+权威状态  │
│ 玩家C(手机)   │ ◄───────────────► │                  │
└─────────────┘                    └──────────────────┘
```

- **为什么不用房主当服务器**：浏览器页面无法监听端口，房主必须是原生客户端——那房主关游戏全房间掉线，体验差
- **关键红利**：服务器用 Godot 无头模式跑，`TurnStateMachine`/`GameConfig`/`Card`/`Deck` **现有脚本原样复用**，只加一层网络协议——规则改动永远只改一处，不会出现"本地和联机规则不一致"

### 保密性：服务器权威 + 手牌不外发

服务器持有全部状态，**只给每个客户端发它该看的**：自己的手牌（明文）、别人的手牌（只发张数）。休想牌持有信息天然保密——正好符合 v0.9.1 匿名响应窗口的设计（服务器定时广播"响应窗口开/关"，谁有牌只有玩家自己知道）。

## 二、客户端需要改什么（工程侧）

| 模块 | 改动 | 量级 |
|---|---|---|
| `main.gd` | 拆成"大厅 UI"（昵称/创建房间/输入邀请码）+ "对局 UI"（现有内容改成只渲染自己视角） | 中 |
| 输入来源 | 现在是"当前回合的人点这台设备"；改成"点卡 → 发消息给服务器 → 服务器广播新状态" | 中 |
| 响应窗口 | 3 秒（v0.9.3，原 8 秒）服务器计时广播：`T_RESPONSE_WINDOW(seconds)` + 每次视图带 `response_left_ms`；出牌者本人不可反制 | 小 ✅已实现 |
| 渲染 | 对手槽从"读本地状态"改成"读服务器快照"；飞牌/爆炸特效照旧 | 小 |
| **不变** | 卡牌逻辑、状态机、数值、动画、特效全部原样 | — |

新增：`scripts/net/net_client.gd`（连接/重连/收发）、`scripts/net/protocol.gd`（消息编解码）。

## 三、服务器需要什么（新增）

```
server/
├── server_main.gd      # 无头入口：起 WebSocketServer(默认 8920 端口)
├── room_manager.gd     # 房间：创建(6位邀请码)/加入/满员/房主转移/空房回收
├── net_session.gd      # 每个连接：昵称、所在房间、心跳
└── （直接 extends 现有 TurnStateMachine，桥接网络消息 ↔ 状态机调用）
```

消息协议（第一版，JSON over WebSocket，够用且好调）：

| 客户端 → 服务器 | 服务器 → 客户端 |
|---|---|
| create_room / join_room(code) / leave | room_created / room_state(座位表) / game_start |
| play_card(index, target?) / draw | state_update(手牌/牌数/牌堆数/当前回合) |
| respond_wish(true/false) | log_message / response_window(open, seconds) |
| confirm_bomb(pos) | bomb_exploded(name) / game_over(winner) |

断线重连：掉线 60 秒内凭 sessionId 重进原座位，房间等他。

## 四、你需要准备什么（按优先级）

### 必须的

1. **一台云服务器**（唯一要花钱的东西）
   - 配置：2核2G 足够（无头 Godot 服务器内存占用 ~100MB，一个房间一局游戏状态 < 1MB，跑几十个房间无压力）
   - 推荐：腾讯云/阿里云轻量应用服务器，**30-60 元/月**，新用户首年常有优惠
   - 系统：Ubuntu 22.04，装 Godot 4.7.2 无头版 + 导出模板（我可以远程帮你部署）
2. **一个域名**（推荐但可后置）
   - 用 IP+端口直连也能玩（测试期够用）
   - 但要 **HTTPS（wss://）** 和 **微信内打开** 就必须域名 + ICP 备案（腾讯云备案免费，流程 1-2 周）
3. **拍板：玩家身份方案**（二选一）
   - **A. 昵称即玩**（推荐先做）：输个昵称就能进房，零门槛，适合朋友局；防不了恶意重名/顶号
   - B. 账号系统：手机号/微信登录，能存战绩、防顶号，但要多做注册登录+后端存储，工期翻倍
   - 建议：M2 先 A，战绩系统放 M3

### 建议的

4. **拍板：房间规则**——默认沿用本地规则（2-5 人、v0.9.2 数值、10-15 分钟）；要不要加"自定义人数上限""观战"？（建议都放 M3）
5. **美术接入**——联机上线是给外人玩的门面，建议联机开发期间把 `assets/art/` 的卡面接入（并行进行，不冲突）

### 不需要准备的

- ❌ 不需要数据库（房间和状态全在内存里，重启即清空）
- ❌ 不需要第二套规则代码（服务器复用现有 GDScript）
- ❌ 不需要担心并发性能（回合制 + 朋友局规模，单机跑几十个房间毫无压力）

## 五、开发里程碑（拍板后执行）

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M2.1 | 协议+服务器骨架：房间创建/加入/开始 | 两台设备能进同一房间看到座位表 |
| M2.2 | 对局同步：出牌/抽牌/爆弹暗置全流程 | 完整联机打完一局（本机开两个浏览器窗口即可测） |
| M2.3 | 休想响应窗口+断线重连+掉线托管 | 拔网线重进能回到原座位继续 |
| M2.4 | 部署上线：服务器安装+进程守护+（可选）域名 HTTPS | 朋友用链接远程开一局 |

预计主体工作量在 M2.1-M2.2（客户端改造是重点），M2.3/M2.4 是收尾。
